# Implementation Plan: Mahrukh Fumigation Services — Company Homepage

**Branch**: `001-company-homepage` | **Date**: 2026-09-16 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-company-homepage/spec.md`

## Summary

Build a single-page, statically-rendered Next.js marketing site for Mahrukh Fumigation Services with anchor-linked sections (header/nav, hero with marquee + trust indicators, about/executive, services, institutional experience/organizations served, why-Mahrukh, contact/get-a-quote, footer), plus a floating "Ask Mahrukh AI" chatbot backed by a server-side Next.js Route Handler that calls the Google Gemini API (free-tier model) with strict grounding, ephemeral conversations, and graceful degradation on any provider failure. All business content is sourced directly from `company-facts.md` into typed constants used by both the page and the chatbot's grounding context, so the two can never drift. Illustrative visuals (FR-059–FR-067) are optional, generic, sparingly used, and never block a deploy. The site uses the already-locked stack (Next.js, TypeScript, Tailwind CSS, shadcn/ui, Lucide, Framer Motion, Vercel) with one new dependency — a Gemini client — already approved via ADR-0001.

## Technical Context

**Language/Version**: TypeScript 5.x on Next.js 14+ (App Router), Node.js 20 LTS runtime
**Primary Dependencies**: Next.js, React 18, Tailwind CSS, shadcn/ui, lucide-react, framer-motion, `@google/generative-ai` (official Gemini SDK, server-only)
**Storage**: N/A — no database. Chatbot conversation state lives only in the browser session (React state), never persisted server-side (FR-058)
**Testing**: TypeScript strict mode + ESLint for static correctness; Vitest + React Testing Library for component/unit tests of content-rendering and the chatbot state machine; a small Playwright smoke suite for the cross-cutting acceptance scenarios that unit tests can't cover (keyboard navigation, `prefers-reduced-motion`, contact links, chatbot fallback). Kept intentionally light — this is a small marketing site, not a test-heavy application (Constitution Principle XII)
**Target Platform**: Modern desktop and mobile browsers, deployed on Vercel
**Project Type**: single (one Next.js app; the chatbot backend is a Route Handler inside the same app, not a separate service)
**Performance Goals**: Homepage primary content interactive within ~3s on a typical mobile connection (SC-004); Lighthouse Performance/Accessibility/SEO/Best-Practices scores in the "good" range (≥90) as a working target, not a contractual SLA
**Constraints**: Zero ongoing cost for the chatbot (Gemini free tier only, no billing — FR-055); no secrets in client bundles (FR-049); no database anywhere in the feature (FR-058); core content and contact paths must work with JavaScript, images, or the chatbot absent (FR-053, edge cases)
**Scale/Scope**: One marketing home page for a small local business; low expected traffic; chatbot request volume expected to comfortably fit free-tier quota given a basic per-session/IP rate limit

## Logo Asset Handling

Per Constitution Principles IV and XIII and spec FR-001/FR-013/FR-029/FR-067: the existing physical letterhead logo is scanned/photographed, then cleaned up (background removal, straightening, light color correction only — no redesign, no re-drawing, no re-typesetting of the wordmark) to produce a transparent-background raster (PNG) and, if feasible without altering the design, an SVG/vector trace. Output lives in `public/logo/` in at least two sizes (header-scale, footer-scale) so header/footer don't need runtime scaling artifacts. This is an **asset-preparation task**, tracked in `/sp.tasks`, not a design task — no new logo is created if the cleanup isn't perfect; the existing design is preserved as closely as technically possible. If no source scan is available yet when implementation starts, the header/footer render with a clearly-labeled placeholder box (not a fabricated logo) so `/sp.implement` is not blocked; swapping in the real asset is a one-file change.

## Illustrative Visual Strategy

Per FR-059–FR-067: at most a small, fixed number of illustrative visual slots exist in the component tree (Hero background/side visual, optionally one in "Why Mahrukh" or "Institutional Experience"). Each slot is rendered through the shared `illustrative-visual.tsx` wrapper, which:
- Accepts an optional image; if none is supplied, renders a brand-colored gradient/pattern + Lucide icon instead (never blocks a build or deploy — FR-064).
- Applies a required generic `caption`/`alt` prop drawn only from the approved label set (e.g., "Professional Commercial Fumigation") — the component's TypeScript props make an empty or missing label a type error, not a runtime guess.
- Never accepts a "location" or "client" prop — there is structurally no field to put "NBP Branch" or "Meezan Bank Site" into (FR-061).
- Applies `loading="lazy"` automatically for any instance below the fold, and uses `next/image` for format/responsiveness (FR-066).
Sourcing actual visuals (AI-generated per the approved subject list, or genuine company photos if supplied later) is a content task for `/sp.tasks`, independent of and non-blocking for the component/logic work.

## Gemini Chatbot Integration

- **Server-side only**: `lib/gemini/client.ts` is imported exclusively by `app/api/chat/route.ts`. It reads `process.env.GEMINI_API_KEY` and `process.env.GEMINI_MODEL` (defaulting to a documented free-tier-eligible model name) at request time; neither this module nor the key is ever imported by any `"use client"` component (FR-049).
- **Request flow**: browser → `POST /api/chat` `{ message, quickSuggestion? }` → route handler applies the rate limiter (`lib/gemini/rate-limit.ts`) → assembles the system prompt from `lib/content/chatbot-knowledge.ts` (grounded strictly in `company-facts.md`-derived content, FR-041) → calls Gemini → returns `{ reply }` on success.
- **Failure mapping (FR-056/057)**: any non-2xx from Gemini, a thrown SDK error, a timeout, or the rate limiter rejecting a request all map to the **same** generic JSON shape, e.g. `{ status: "unavailable", message: "I'm temporarily unavailable. Please contact Mahrukh Fumigation Services directly by phone, WhatsApp, or email." }` with an HTTP 200 (so the client doesn't need special-case handling per error type) — the route handler logs the real error server-side only (for the owner's/developer's own diagnostics) and never forwards status codes, provider error bodies, or stack traces to the response body.
- **Client states** (`use-chatbot.ts`): `idle → loading → (success | unavailable)`, plus a client-side `error` state for network failures (fetch rejects) before a response is even received — all four states render distinct, calm UI per FR-048, and `unavailable`/`error` both render the same contact-option footer.
- **Off-topic/out-of-scope handling**: enforced primarily via the system prompt (explicit instruction: answer only from the provided business context; if the question is unrelated or the answer isn't in the context, say so and point to contact) — this is a prompting/grounding concern documented in `chatbot-knowledge.ts`, not a separate code path, since Gemini itself produces the "I don't have that information" response when correctly grounded and instructed (FR-043/044).
- **No persistence**: chat history lives only in React state in `use-chatbot.ts` for the current page session; nothing is written to a database, file, or external logging service (FR-058).
